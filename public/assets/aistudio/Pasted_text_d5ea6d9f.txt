# 4. ACCOUNT REGISTRATION AND AUTHENTICATION

Create a secure username-based authentication system.

### Registration process

1. User opens NEXORA.
2. User selects Create Account.
3. User enters their Gmail/email address.
4. System sends a six-digit verification OTP.
5. User enters the OTP.
6. System validates the OTP.
7. User chooses a unique username.
8. User enters a display name.
9. User creates a strong password.
10. User optionally uploads a profile picture.
11. Account is successfully created.

### Username requirements

- Every username must be unique.
- Usernames must be searchable.
- Username changes must be controlled.
- Support username availability checking.
- Use a normalized username field for uniqueness.
- Users must be discoverable without knowing their email address.
- Never expose private email addresses through public profile searches.

Example usernames:

- @ShadowKing
- @MysticSoul
- @MoonLight
- @CyberGhost
- @GalaxyQueen

### Authentication security

Implement:

- Secure password hashing using Argon2id.
- Short-lived OTP verification codes.
- OTP expiration.
- OTP resend cooldown.
- Rate limiting.
- Brute-force protection.
- Secure session management.
- Password reset through verified email.
- Account logout.
- Device/session management.

Use a transactional email service or properly configured SMTP provider. Gmail addresses can be used for verification, but do not depend on a personal Gmail account as the application's authentication database.

Never store plaintext passwords or OTPs.

# 15. END-TO-END ENCRYPTION — CRITICAL

Security is a mandatory core requirement, not an optional feature.

Implement real end-to-end encryption.

### Private conversations

Use an established, audited implementation of the Signal Protocol or an appropriate compatible cryptographic library.

Support:

- Identity keys.
- Prekeys.
- Session establishment.
- Forward secrecy.
- Post-compromise security where supported.
- Authenticated message encryption.
- Device-specific key management.
- Key rotation.
- Secure session recovery design.

### Group conversations

Use a suitable audited group encryption protocol, such as Messaging Layer Security (MLS), or another established group encryption design.

Support:

- Secure group key establishment.
- Membership changes.
- Key updates.
- Member removal.
- Secure group state synchronization.
- Protection against unauthorized historical access.

### Media encryption

- Encrypt media locally before uploading.
- Generate secure media encryption keys.
- Store encrypted media only.
- Share media keys securely through encrypted conversations.
- Verify media integrity.

### Server limitations

The server must never have access to plaintext private messages, plaintext encryption keys, or decrypted media.

Only store encrypted message payloads and the metadata strictly necessary for delivery and operation.

Be careful with metadata: end-to-end encryption does not automatically conceal sender identities, timestamps, group membership, IP addresses, or other server-visible information.

### Security verification

Do not claim the application is end-to-end encrypted until encryption is actually implemented and tested.

Provide a documented security architecture, threat model, key lifecycle, and independent security review plan.

Never implement homemade encryption.
